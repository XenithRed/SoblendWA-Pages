Bots de WhatsApp con un motor en Rust.

SoblendWA habla el protocolo de WhatsApp Web sin navegador: WebSocket, Noise, nodos binarios y Signal. Lo usas desde Rust, Node.js, Python o cualquier lenguaje que hable WebSocket o HTTP. Aquí está todo, desde el primer bot hasta correr cincuenta cuentas en un proceso.

Antes de usarlo#

Riesgo de bloqueo

SoblendWA es independiente y no está afiliado a WhatsApp ni a Meta. Automatizar una cuenta puede ir contra sus Términos de Servicio y provocar un bloqueo. Lee el aviso y qué está probado.

Inicio rápido

En cinco minutos tendrás un bot que responde a !ping en tu propio WhatsApp.

Lo que necesitas#

  • Un teléfono con WhatsApp, para escanear el QR. Usa una cuenta de pruebas si puedes.
  • Rust, Node.js o Python instalados, según el lenguaje que elijas.

1. Escribe el bot#

use soblendwa::{Client, Event, FileStore};

#[tokio::main]
async fn main() -> soblendwa::Result<()> {
    let store = FileStore::open("session").await?;
    let (client, mut events) = Client::builder()
        .store(store)
        .push_name("Mi Bot")
        .build()
        .await?;
    client.connect().await?;

    while let Some(event) = events.recv().await {
        match event {
            Event::Qr(code) => println!("Escanea este QR: {code}"),
            Event::Connected => println!("Conectado como {:?}", client.me()),
            Event::Message(msg) if !msg.info.from_me => {
                if msg.text() == Some("!ping") {
                    let ms = msg.info.elapsed().as_secs_f64() * 1000.0;
                    client.reply(&msg, format!("Pong\n{ms:.2} ms")).await?;
                }
            }
            Event::LoggedOut { reason, .. } => {
                println!("Sesión cerrada: {reason}");
                break;
            }
            _ => {}
        }
    }
    Ok(())
}
const { SoblendWA } = require('soblendwa-node')

async function main() {
  const bot = await SoblendWA.create({ store: { type: 'sqlite', path: 'session/auth.db' } })

  bot.on('qr', ({ code }) => console.log('Escanea este QR:', code))
  bot.on('connected', () => console.log('Conectado como', bot.me))
  bot.on('message', async (message) => {
    if (message.info.fromMe) return
    if (message.text === '!ping') await bot.reply(message, `Pong\n${bot.elapsed(message).toFixed(2)} ms`)
  })

  await bot.connect()
}

2. Vincula tu teléfono#

El texto del evento qr es el contenido del código QR, no una imagen. Conviértelo en imagen con cualquier librería de QR, como qrcode-terminal en Node.js o qrcode en Python, o usa un código de 8 caracteres.

  1. Ejecuta el bot.
  2. En el teléfono, abre WhatsApp > Dispositivos vinculados > Vincular un dispositivo.
  3. Escanea el QR. El bot se reinicia solo una vez y emite connected.
  4. Desde otro número, envía !ping a la cuenta vinculada.
  5. Recibes Pong y el tiempo que tardó el bot.

Mensajes viejos

Al conectar te pueden llegar mensajes de cuando el bot estaba apagado. Para no responder comandos de hace horas, ignóralos con is_stale.

3. Qué acaba de pasar#

Tu bot abrió un WebSocket con WhatsApp, verificó su certificado y se registró como un dispositivo vinculado más, igual que WhatsApp Web. Las claves se guardaron en la carpeta o base de datos que elegiste, así que la próxima vez conectará sin QR.

Todo lo que ocurre llega como un evento. Tu bot reacciona a los que le interesan y llama métodos para actuar.

Vincular y sesión

Cómo se vincula una cuenta, cuánto dura la sesión y qué pasa cuando se corta la conexión.

Vincular con QR#

Después de connect(), si la sesión no está vinculada, llega un evento Qr con el contenido del código. El primero dura 60 segundos y los siguientes 20. Mientras no se escanee, llegan códigos nuevos. Si se agotan, la conexión termina con el motivo QrTimeout y, con la reconexión automática activada, empieza otra tanda de códigos.

Al escanearlo llegan, en este orden:

EventoQué significa
PairSuccess { id, lid, platform, business_name }El teléfono aprobó la vinculación
Disconnected { reason: RestartRequired, reconnecting: true }Reinicio normal que pide WhatsApp tras vincular. No es un error
ConnectedLa sesión está lista para enviar y recibir

Sirve cuando no puedes escanear, por ejemplo en un servidor sin pantalla. Pide el código después del primer evento qr y escríbelo en Dispositivos vinculados > Vincular con el número de teléfono.

Cuánto dura la sesión#

La sesión queda en el almacenamiento que elegiste y sobrevive a los reinicios. Termina solo si cierras la vinculación desde el teléfono, si llamas a logout() o si WhatsApp la invalida. En esos casos llega LoggedOut { reason, cause, code }, los datos se borran y el siguiente connect() muestra un QR nuevo.

Lo que WhatsApp no dice

Cuando el teléfono quita un dispositivo, WhatsApp no dice si lo hizo el dueño a mano o si fue el teléfono por su cuenta. removedFromPhone cubre los dos casos. Un bloqueo de la cuenta no llega como cierre de sesión: llega como accountBlocked, y la sesión se conserva.

Protege tu carpeta de sesión

Contiene las claves de tu cuenta. Quien la tenga puede enviar y leer mensajes en tu nombre, así que nunca la subas a Git ni la compartas.

Una sesión, un proceso

Dos procesos no pueden usar la misma sesión a la vez. El segundo expulsa al primero, que recibe el motivo Replaced, y uno puede consumir los mensajes pendientes del otro. Detén el bot antes de arrancar otra copia.

Conceptos

Las pocas ideas que necesitas para entender todo lo demás.

Dispositivo vinculado#

SoblendWA es un dispositivo más de tu cuenta, como WhatsApp Web. No se registra como teléfono: necesita un teléfono real que apruebe la vinculación, con WhatsApp instalado.

JID: la dirección de todo#

Cada cuenta, grupo o canal tiene un JID con la forma usuario:dispositivo@servidor.

EjemploQué esCómo crearlo en Rust
5215512345678@s.whatsapp.netUna cuenta, por su númeroJid::phone("5215512345678")
5215512345678:3@s.whatsapp.netEl dispositivo 3 de esa cuentajid.with_device(3)
100000000000001@lidUna cuenta, por su LIDJid::lid("100000000000001")
120363000000000001@g.usUn grupoJid::group("120363000000000001")

Un JID también se puede leer desde un texto:

let jid: Jid = "5215512345678@s.whatsapp.net".parse()?;
let same = jid.same_user(&Jid::phone("52 1 55 1234 5678"));

Jid::phone conserva solo los dígitos, así que acepta números con espacios o signos. En Node.js, Python y el servidor, cualquier parámetro chat acepta un JID completo o solo el número.

LID: cuando WhatsApp oculta el número#

WhatsApp identifica a muchas cuentas con un LID, un identificador que no revela el teléfono, sobre todo en grupos. Una misma persona puede aparecer por su número o por su LID.

SoblendWA resuelve ambos por ti. Cada mensaje trae info.sender_phone e info.sender_lid, y group.is_admin(&sender) funciona con cualquiera de los dos. Si WhatsApp no comparte el número de alguien, sender_phone queda vacío; el LID sigue sirviendo para identificarlo.

Puedes consultar la relación en cualquier momento, y te avisa cuando descubre un par nuevo, así puedes unir perfiles en tu base sin migraciones.

let lid = client.lid_for_phone(&Jid::phone("5215511111111")).await?;
if let Event::LidMapping { phone, lid } = event {
    println!("{phone} y {lid} son la misma persona");
}
const lid = await bot.lidForPhone('5215511111111')
const phone = await bot.phoneForLid('100000000000001@lid')
bot.on('lidMapping', ({ phone, lid }) => console.log(phone, 'y', lid, 'son la misma persona'))
lid = await bot.lid_for_phone("5215511111111")
phone = await bot.phone_for_lid("100000000000001@lid")

@bot.on("lidMapping")
def linked(event):
    print(event["phone"], "y", event["lid"], "son la misma persona")
const lid = await bot.lidForPhone('5215511111111')
bot.on('lidMapping', ({ phone, lid }) => console.log(phone, 'y', lid, 'son la misma persona'))

lidMapping llega una sola vez por par, la primera vez que se conoce. Al vincular puede llegar muchas veces seguidas, una por cada contacto del historial.

Chat y remitente#

info.chat es la conversación y info.sender es quien escribió. En un chat privado suelen coincidir; en un grupo, chat es el grupo y sender es la persona. Responde siempre a chat.

Identificador y clave de un mensaje#

Cada mensaje tiene un id de texto. Para editarlo, borrarlo o fijarlo necesitas su clave (MessageKey): el chat, el id, si es tuyo y, en grupos, quién lo envió. msg.key() te la da hecha.

Mensajes envueltos#

WhatsApp mete los mensajes dentro de otros: ephemeral, viewOnce, documentWithCaption, hijos de álbum, Meta AI, estados de grupo. SoblendWA los desenvuelve, así que msg.text(), msg.message.media() y msg.quoted() funcionan igual en todos. Si necesitas el original, está en msg.raw.

Eventos#

Todo lo que ocurre llega por un único canal de eventos: mensajes, recibos, cambios de grupo, desconexiones. En Rust es un enum, y en los demás lenguajes es JSON con un campo type. La lista completa está en Eventos.

Colas por chat#

Los chats distintos se atienden en paralelo y cada chat conserva su orden, al recibir y al enviar. Un texto nunca espera detrás de un video pesado de otro chat, y en el mismo chat los mensajes salen en el orden en que los pediste.

En Node.js, Python y por WebSocket el orden se fija en el momento de la llamada, así que bot.sendText(chat, 'uno'); bot.sendText(chat, 'dos') sin await sale en ese orden. Cada llamada toma un turno en su chat; mientras espera no gasta CPU, y al terminar despierta solo a la siguiente.

Los archivos empiezan a subir en cuanto los pides, sin esperar turno; lo que espera es la entrega. Así varias fotos al mismo chat suben a la vez y llegan en orden.

Sesiones, cuentas y almacenamiento#

Una sesión es una cuenta vinculada con sus claves, guardadas en un store. Puedes tener varias en el mismo proceso, cada una con su propio cliente. El servidor maneja varias a la vez por nombre.

Menciones#

Una mención necesita dos cosas: el @número en el texto y el JID en la lista de mencionados.

client.send_message(&grupo, Message::text("Atención a todos").mention_all()).await?;
await bot.sendText(chat, 'hola @5215511111111', { mentions: ['5215511111111'] })
await bot.sendMentionAll(grupo, 'Atención a todos')

await bot.sendText(chat, 'hola @5215511111111', { mentions: ['5215511111111'] })
await bot.sendMentionAll(grupo, 'Atención a todos')

Mensajes que no se pudieron descifrar#

Si un mensaje no se puede descifrar llega Event::UndecryptableMessage { info, error }, y SoblendWA pide un reintento al remitente y una copia a tu teléfono. Si después llega bien, recibes Event::Message normal y Event::MessageRecovered { id, chat, sender }.

Si pasado el plazo sigue sin llegar, recibes Event::MessageLost { id, chat, sender, error, waited }, y se cuenta en stats().lost. Así sabes cuántos mensajes tu bot nunca leyó, en lugar de suponerlo. Si llega más tarde, igual recibes MessageRecovered y lost baja.

MétricaQué cuenta
stats().undecryptableLos que no se pudieron descifrar al llegar
stats().awaiting_recoveryLos que siguen esperando el reintento
stats().recoveredLos que llegaron bien tras el reintento
stats().lostLos que no llegaron dentro del plazo

El plazo es de 10 minutos y se cambia con .retry_deadline(...) en Rust o retryDeadlineSecs en Node.js y Python. El caso más común en grupos es missing sender key: el remitente no le envió al bot su clave de grupo, y el reintento se la pide.

La espera se guarda en el store, así que sobrevive a un reinicio: al volver, el bot sigue esperando lo que quedaba del plazo, y si el plazo ya pasó emite MessageLost al arrancar. Un mensaje que llega después del reinicio sigue dando MessageRecovered.

Cómo funciona#

  • La consulta sale de tu servidor. Para generar la vista previa, el bot abre la página, como hace el teléfono en la app oficial. Si repite enlaces de desconocidos y no quieres eso, usa enabled: false.
  • Protegido contra enlaces maliciosos. Nunca consulta hosts privados: 127.0.0.1, la red interna, el servicio de metadatos de la nube (169.254.169.254), localhost, *.local ni *.internal. También revisa cada redirección y a qué IP resuelve el dominio, así un dominio público que apunte a tu red interna tampoco pasa.
  • Dos miniaturas. Una pequeña dentro del mensaje y otra nítida de hasta 1200 px, subida cifrada. Si la subida falla, el mensaje sale igual con la pequeña. La nítida aún es Experimental
  • Reutiliza lo que ya hizo. Un enlace repetido no vuelve a consultar la página, por 1 hora, ni a subir la miniatura.
  • Nunca frena un envío. Si la página falla o no responde, sale una tarjeta mínima con el dominio.
  • Imágenes hostiles. La imagen se decodifica con límites de tamaño y memoria.

Reconexión#

La espera crece y tiene un margen aleatorio, para que cien sesiones no se reconecten en el mismo milisegundo.

Fallo seguidoEspera

Segundo1 s más un margen aleatorio

Siguientes4 s, 8 s… hasta 60 s, más un margen aleatorio

Se apaga con .auto_reconnect(false). El keepalive envía un ping cada 15 segundos y, si no hay respuesta en 8, reconecta. El servidor además escalona el arranque de las sesiones.

Límite de envíos#

Un bug que manda mensajes en bucle no se convierte en spam. Cada envío gasta una ficha del total de la cuenta y otra de su chat; las fichas vuelven poco a poco, al ritmo por minuto de cada límite.

Campo de SendLimitPor defectoQué limita
per_minute, burst240, 60Mensajes por minuto y ráfaga máxima, en total
per_chat_per_minute, per_chat_burst40, 15Lo mismo en cada chat privado
per_group_per_minute, per_group_burst40, 15Lo mismo en cada grupo
max_wait30 sCuánto puede esperar un envío que pasó el límite

Qué pasa al pasarse#

El envío espera en la fila de su chat hasta que le toque una ficha, y sale en el mismo orden en que lo pediste. Los demás chats siguen sin esperar, salvo que se acabe el límite total. Así una ráfaga de comandos en un grupo activo se reparte en el tiempo en lugar de fallar:

  • Con el límite por defecto, un grupo puede recibir 15 mensajes seguidos y después uno cada 1,5 s.
  • Cada envío que tuvo que esperar se cuenta en stats().rate_delayed, y su espera aparece en la fase queued de los tiempos por fase.
  • Si la ficha no llega dentro de max_wait, contando desde que llamaste, falla con Error::RateLimited { chat, retry_after } (código RATE_LIMITED) y se cuenta en stats().rate_limited. Si desde el principio se ve que no va a alcanzar, falla en el acto en lugar de esperar para nada.
  • Con max_wait en cero vuelve el comportamiento de antes: falla en el acto, antes de subir ningún archivo.

Si tu bot vive en grupos muy activos, sube solo el límite de grupos y deja igual el de chats privados, que es donde un bucle hace más daño:

use std::time::Duration;
use soblendwa::SendLimit;

    per_group_per_minute: 90,
    per_group_burst: 30,
    max_wait: Duration::from_secs(20),
    ..Default::default()
};
let (client, events) = Client::builder().store(store).send_limit(Some(limite)).build().await?;

.send_limit(None) lo desactiva. Bajar los límites reduce el riesgo, pero no hay ningún ritmo que garantice que WhatsApp no bloquee una cuenta, y nadie publica cuánto tolera en un grupo.

Reinicios sin pérdidas#

Cada mensaje se guarda en un outbox hasta que WhatsApp confirma que lo recibió. Si se cae la conexión o reinicias el proceso, se reenvía al reconectar con el mismo id, y un mensaje que sigue en vuelo no se reenvía.

  • client.pending_sends() muestra lo que está esperando: id, chat, queued_at y attempts.
  • stats().outbox_resent cuenta los reenvíos.
  • .outbox(false) lo desactiva.

Si tu bot usa otra librería al otro lado

Un reenvío lleva el mismo id. SoblendWA descarta los duplicados al recibir, y los bots hechos con otras librerías deben hacer lo mismo.

Reintentos después de reiniciar#

Lo enviado se conserva hasta dos días, así un contacto que no pudo descifrar un mensaje puede pedirlo de nuevo aunque el bot se haya reiniciado.

Al revés también: los mensajes que el bot no pudo descifrar y siguen esperando su reintento se guardan en el store (awaiting-retry). Si reinicias a la mitad, la espera sigue donde estaba, y MessageLost o MessageRecovered llegan igual.

Un fallo no tumba todo#

Si un handler entra en pánico, se registra, se cuenta en stats().panics y la sesión sigue. Cada sesión del servidor es independiente: si una se cuelga abriendo su almacenamiento, las demás siguen.

Recuperación de mensajes#

Si un mensaje no se puede descifrar, SoblendWA pide un reintento al remitente y una copia a tu teléfono a la vez. Cuando llega bien, emite Event::MessageRecovered. Si no llega dentro del plazo, emite Event::MessageLost y lo cuenta en stats().lost, así sabes cuántos se perdieron de verdad. Los detalles están en Recibir mensajes. Esto está probado de punta a punta contra el WhatsApp falso, y aún falta confirmarlo con una cuenta real. Experimental

Latencia#

  • msg.info.elapsed() mide cuánto lleva el mensaje dentro del bot, desde que llegó del socket. Incluye descifrarlo.
  • client.latency() devuelve al instante la latencia de red medida en segundo plano.
  • client.ping() hace una medición nueva y tarda un viaje de ida y vuelta.

La primera vez que el bot le escribe a un chat nuevo, tiene que pedir los dispositivos del destinatario y sus claves: uno o dos viajes de ida y vuelta, igual que WhatsApp Web. Después todo queda guardado y los envíos solo cuestan el cifrado local.

El tiempo que ves en el teléfono es la suma del viaje de tu teléfono a WhatsApp, unos 0,05 ms del bot, y el viaje de WhatsApp al bot y de vuelta. Esos viajes dependen de la distancia física y de tu conexión, y ningún código puede bajarlos de lo que permita la red.

Un bot con base de datos, red y multimedia#

  • Arranque. Antes de medir, el bot se cierra y vuelve a abrir desde su base, sin vincular de nuevo.

En la versión anterior los envíos al mismo chat sin await podían salir desordenados; ahora salen en el orden en que se llamaron, y eso cuesta algo de velocidad cuando todos van al mismo chat. Entre chats distintos no hay espera. En un bot real, WhatsApp limita mucho antes de llegar a estas cifras.

Por qué es rápido#

Desde que llega un mensaje hasta que sale la respuesta, el bot tarda unos 0,05 ms en un chat conocido.

  • Sin esperas de red en chats conocidos. Las sesiones, los dispositivos y los datos de los grupos se guardan en disco y se usan al instante, aunque reinicies el bot. Se actualizan en segundo plano y cuando WhatsApp avisa de un cambio. Al conectar se precargan tus grupos y los dispositivos de sus miembros.
  • Grupos grandes rápidos desde el primer mensaje. Las consultas de claves y dispositivos salen en paralelo, en un solo viaje de red, y las sesiones Signal se crean usando todos los núcleos: 1000 dispositivos en unos 0,1 s en lugar de 0,4 s.
  • Socket sin demoras. TCP_NODELAY evita que el sistema retenga mensajes pequeños. El lector y el escritor tienen cada uno su propio cifrador AES-GCM y no comparten locks.
  • Arranque rápido. La versión de WhatsApp Web se recuerda y se actualiza en segundo plano.
  • Almacenamiento sin bloqueos. FileStore escribe en un log de solo-escritura únicamente lo que cambió y compacta de vez en cuando. Los backends SQL y Redis agrupan las escrituras en segundo plano.
  • Colas por chat. Los chats distintos van en paralelo y cada chat conserva su orden.
  • Multimedia reutilizada. El mismo archivo no se vuelve a cifrar ni a subir.
  • Eventos en lotes. Node.js y Python reciben todos los eventos que estén listos en una sola llamada, como un solo texto JSON, en vez de una promesa por evento.
  • JSON escrito directo. Los mensajes, recibos y confirmaciones se escriben como texto sin pasar por un árbol de objetos intermedio.
  • Menos reservas de memoria. Los módulos de Node.js y Python y el servidor usan mimalloc, y los JID se formatean sin la maquinaria de format!.
  • Sesiones que cargan al instante. La clave pública del ratchet se guarda junto a la privada, así que leer una sesión no repite una multiplicación de curva. Al firmar en grupos, la clave de Edwards se calcula una vez por sender key.
  • Turnos por chat. Cada envío toma su lugar al llamarse y, al terminar, despierta solo al siguiente de ese chat.
  • Sin código inseguro. #![forbid(unsafe_code)], y el decodificador binario está probado contra cientos de miles de entradas hostiles.

account permite guardar varias cuentas en la misma base. Con FileStore, usa una carpeta por cuenta. Si no indicas un store, Rust usa memoria, y Node.js y Python usan la carpeta session.

Las credenciales y las claves de la cuenta son secretos. Protege el acceso a tu base de datos y a tu carpeta de sesión como protegerías una contraseña.

Cómo funciona por dentro#

Todos los backends de Rust comparten el mismo núcleo, BatchedStore: las lecturas salen de memoria después de la primera vez, y las escrituras se agrupan en una sola transacción, o un solo pipeline en Redis, en segundo plano. Si una clave cambia mil veces antes de escribirse, solo se escribe el último valor. Enviar un mensaje nunca espera a la base de datos. client.disconnect() vacía lo pendiente antes de salir.

Multimedia compartida entre cuentas#

Por defecto, cada cuenta recuerda lo que subió en su propio store. Con un store de multimedia compartido, todas tus cuentas reutilizan lo que ya subió cualquiera de ellas, y lo recuerdan tras reiniciar. Si tus subbots envían la misma imagen de un comando, solo la primera la sube.

Probar con una copia de tu base#

Antes de tocar tus sesiones de verdad, hazlo con una copia. Así nadie tiene que volver a vincular si algo falla.

  1. Copia la base de zapo: mongodump --uri "mongodb://…" --db bot --archive=bot.archive y mongorestore --uri "mongodb://…" --archive=bot.archive --nsFrom "bot.*" --nsTo "bot_copia.*".
  2. Corre importZapo con { check: true } sobre bot_copia y revisa que failed esté vacío y que los números de sesiones y claves tengan sentido.
  3. Detén el subbot que vas a probar en zapo. Nunca uses una sesión en dos procesos a la vez.
  4. Importa esa sesión a un store vacío de SoblendWA y arranca el subbot con SoblendWA. Prueba privados, grupos, multimedia y comandos.
  5. Para volver, detén SoblendWA y corre rollbackZapo hacia la base desde la que arrancará zapo. Arranca zapo y comprueba que sigue enviando y recibiendo.
  6. Cuando todo funcione, repite con la base real, cuenta por cuenta.

Lo que todavía no está probado

La conversión desde @zapo-js/store-mongo y MongoStore pasan contra un MongoDB real en el CI, pero con documentos de prueba que siguen el esquema exacto de zapo, no con una base que haya escrito zapo de verdad. Por eso la copia es obligatoria. Si tienes un MongoDB de pruebas, corre también SOBLEND_MONGO_URL=mongodb://… cargo test --features "sqlite mongo" --lib mongo -- --ignored.

Cómo se prueba#

tests/zapo/round-trip.cjs hace la migración completa con el zapo de verdad, sin datos armados a mano:

  1. zapo 1.11 vincula un bot contra @zapo-js/fake-server y guarda todo con su propio @zapo-js/store-mongo (o @zapo-js/store-sqlite).
  2. Dos contactos le escriben en privado y en un grupo, y el bot les contesta.
  3. SoblendWA hace el simulacro, importa, se conecta sin volver a vincular y sigue hablando con los mismos contactos: el privado sale como msg, es decir, el mismo ratchet que dejó zapo y no una sesión nueva, y el grupo usa las sender keys de zapo.
  4. rollbackZapo devuelve el estado a la base de zapo, zapo arranca desde ahí y la conversación sigue.

El CI la corre en cada push contra MongoDB 7 y con SQLite. Para correrla tú:

Terminal
npm ci --prefix tests/zapo
node tests/zapo/round-trip.cjs mongo mongodb://127.0.0.1:27017

Antes de migrar tu bot de producción, haz el simulacro y una copia de la base.

Desde Python#

Lo mismo con asyncio. Los métodos son los de Node.js en snake_case, y slow_uploads recibe segundos.

import asyncio
from soblendwa import FakeWhatsApp


async def main():
    fake = await FakeWhatsApp.start()
    bot = await fake.connect("5215511111111")
    ana = await fake.connect("5215522222222")

    await ana.send_text("5215511111111", "!ping")
    mensaje = await bot.wait_for("message", lambda m: m["text"] == "!ping")
    await bot.reply(mensaje, "Pong")

    grupo = await ana.group_create("Pruebas", ["5215511111111"])
    entra = await bot.wait_for("joinedGroup")
    assert entra["via"] == "created" and entra["group"] == grupo["jid"]


asyncio.run(main())

Crear el cliente#

const { SoblendWA } = require('soblendwa-node')

async function main() {
  const bot = await SoblendWA.create({
    store: { type: 'sqlite', path: 'session/auth.db' },
    pushName: 'Mi Bot',
  })

  bot.on('qr', ({ code }) => console.log('Escanea:', code))
  bot.on('connected', () => console.log('Conectado como', bot.me))
  bot.on('message', async (message) => {
    if (message.info.fromMe) return
    if (message.text === '!ping') await bot.reply(message, `Pong\n${bot.elapsed(message).toFixed(2)} ms`)
  })

  await bot.connect()
}

SoblendWA es un EventEmitter. Cada evento se emite por su type, y también como event, y los errores de los handlers como error.

Errores#

Todos los métodos fallan con un SoblendError, que trae code y, si el error viene de WhatsApp, status. Compara siempre code, nunca el texto: el texto puede cambiar entre versiones y el código no.

const { SoblendError } = require('soblendwa-node')

try {
  await bot.groupJoin(enlace)
} catch (error) {
  if (!(error instanceof SoblendError)) throw error

  else if (error.code === 'NOT_FOUND') console.log('El enlace no existe')
  else console.log(error.code, error.status, error.message)
}

Crear el cliente#

import asyncio
from soblendwa import SoblendWA


async def main():
    bot = await SoblendWA.create(store={"type": "sqlite", "path": "session/auth.db"}, push_name="Mi Bot")

    @bot.on("qr")
    def qr(event):
        print("Escanea:", event["code"])

    @bot.on("message")
    async def answer(message):
        if message["info"]["fromMe"]:
            return
        if message["text"] == "!ping":
            await bot.reply(message, f"Pong\n{bot.elapsed(message):.2f} ms")

    await bot.run()

Las opciones de create usan snake_case y se convierten solas. Están en Configuración. Las opciones anidadas también, como link_previews={"timeout_ms": 2000}.

Eventos#

@bot.on("tipo") registra un handler, que puede ser normal o async. "event" recibe todos. bot.run() conecta y atiende los eventos hasta que la sesión termine.

Si prefieres manejar el bucle tú mismo:

await bot.connect()
async for event in bot.events():
    print(event["type"])

Los eventos son diccionarios con los mismos campos que en JSON, en camelCase, como message["info"]["fromMe"]. Un handler que lanza una excepción se registra con logging y no detiene a los demás.

Protocolo WebSocket#

Al conectar a ws://host:8787/ws/<cuenta>?token=… llega primero el saludo y, si hay un QR pendiente, el evento qr.

Saludo
{ "type": "hello", "session": "ventas", "me": "5215512345678:3@s.whatsapp.net", "connected": true, "methods": ["status", "sendText"] }

Después llegan los eventos:

Evento
{ "session": "ventas", "event": { "type": "message", "text": "hola" } }

Para llamar un método, envía un id tuyo, y la respuesta trae el mismo. Las llamadas se atienden en paralelo, así que las respuestas pueden llegar en otro orden.

Llamada
{ "id": 1, "method": "sendText", "params": { "chat": "5215512345678", "text": "hola" } }
Respuesta correcta
{ "id": 1, "result": "3EB0ABC123" }
Respuesta con error
{ "id": 1, "error": { "message": "invalid argument: missing parameter \"text\"", "code": "INVALID_ARGUMENT", "status": null } }

Si un cliente va tan lento que el servidor descarta eventos, recibe {"type":"lagged","missed":N}. El búfer guarda hasta 4.096 eventos por cuenta.

Webhooks#

Con --webhook, cada evento se envía por POST a tu URL, con el mismo JSON que en el WebSocket y un límite de 10 segundos. Si hay --token, va en la cabecera Authorization, y conviene que lo revises para saber que el aviso viene de tu servidor. Si la entrega falla, se registra en los logs y no se reintenta.

Recibir webhooks en Node.js
const http = require('node:http')

http.createServer((request, response) => {
  if (request.headers.authorization !== 'Bearer mi-clave') {
    response.writeHead(401).end()
    return
  }
  let body = ''
  request.on('data', (chunk) => (body += chunk))
  request.on('end', () => {
    const { session, event } = JSON.parse(body)
    console.log(session, event.type)
    response.writeHead(200).end()
  })
}).listen(3000)

Cómo funciona

Qué ocurre por dentro desde que abres la conexión hasta que sale un mensaje.

Conectar#

  1. WebSocket. Se abre un WSS hacia WhatsApp, a través del proxy si lo configuraste, con TCP_NODELAY.
  2. Handshake Noise. Se negocia XX_25519_AESGCM_SHA256 y se verifica la cadena de certificados de WhatsApp y su vigencia. A partir de aquí todo va cifrado.
  3. Inicio de sesión. Si no hay cuenta vinculada, se registra y llegan los QR. Si la hay, se presenta con sus claves.
  4. Preparación. Se suben pre-keys si hacen falta, se sincroniza el app state, y se precargan tus grupos y los dispositivos de sus miembros.
  5. Listo. Llega Event::Connected, y empiezan el keepalive y el vaciado del outbox.

Recibir un mensaje#

  1. Llega un frame cifrado por el WebSocket y se descifra con AES-GCM.
  2. El decodificador lo convierte en un nodo binario, con límites contra entradas hostiles.
  3. Pasa a la cola de su chat, así los chats distintos van en paralelo y cada uno conserva su orden.
  4. Se descifra con Signal: Double Ratchet en privado, Sender Keys en grupos. Si falla, se pide un reintento.
  5. Se descarta si es un duplicado, se resuelven el número y el LID, y se desenvuelve el protobuf.
  6. Se envía el recibo a WhatsApp, y Event::Message llega a tu bot.

Enviar un mensaje#

  1. Límite. Se comprueba el límite de envíos, del total y del chat.
  2. Outbox. El mensaje se guarda, por si se cae la conexión.
  3. Cola. Entra en la cola de su chat, para conservar el orden.
  4. Vista previa. Si trae un enlace, se genera. Nunca frena el envío más de lo configurado.
  5. Dispositivos. Se buscan los del destinatario, en caché, y se crean las sesiones Signal que falten. Es la única parte con esperas de red, y solo la primera vez.
  6. Cifrado. Se cifra para cada dispositivo. En grupos, se usa la sender key.
  7. Confirmación. WhatsApp responde, llega Event::ServerAck con sus tiempos, y el mensaje sale del outbox.

4. Dos semanas#

Deja corriendo live-check.js, o tu bot con un subbot, durante dos semanas en el mismo servidor donde corre zapo. Si se reinicia, el reporte sigue sumando. Cuando quieras ver cómo va:

Terminal
node node_modules/soblendwa-node/live-check.js --resumen prueba-en-vivo/live-check.jsonl

El resumen da los días, los arranques, los mensajes recibidos y enviados, los que no se pudieron descifrar (en porcentaje y por día, para compararlos con zapo), los recuperados, los perdidos de verdad, las reconexiones, la memoria máxima, los bloqueos y cada cierre de sesión con su causa.

Además, el canario entre dos números de prueba, una vez al día, avisa el mismo día si WhatsApp cambió algo.

Más rápido#

Medido en la misma máquina antes y después (pipeline y throughput en las pruebas ignoradas).

  • Eventos hacia Node y Python en lotes, un JSON por lote: el doble de mensajes por segundo al handler, ~35% menos CPU.
  • JSON de mensajes, recibos y acks escrito directo: 18,7 µs → 3 µs.
  • Cargar una sesión Signal sin rehacer su clave pública: 54 µs → 4 µs. Las sesiones viejas cargan igual.
  • Firma de grupo con la clave de Edwards cacheada: ~18% más en grupos.
  • mimalloc en Node, Python y el servidor.
  • Miniaturas: 93 ms → 41 ms para una foto de 1600×1200.
  • Varios archivos al mismo chat suben a la vez y se entregan en orden. Seis subidas de 150 ms: 1,08 s → 0,36 s (uploads_overlap_in_order). Vale para Rust, Node, Python y el servidor.
  • Signal con un lock por contacto en vez de uno por cuenta (signal::bench::contention, release): 32 chats recién reiniciados con un store de 5 ms por lectura, 490 ms → 7 ms; con todo en caché, 99 mil → 210 mil descifrados/s en un hilo y 78 mil → 583 mil en cuatro. Los envíos a grupos también leen sus sesiones a la vez.
  • JIDs formateados sin write!.

Arreglado#

  • create de un grupo nuevo llegaba sin participantes (el saludo que esperaba add nunca salía).
  • Vincular con código daba 400 bad-request: hay que mandar Navegador (Sistema), mandábamos Chrome (SoblendWA). Probado con un teléfono real.
  • send_text / send_image ocupaban 25–31 KB de future y podían desbordar la pila del hilo principal en Windows. Ahora < 2 KB, con una prueba que lo vigila.
  • Una lista de dispositivos vacía quedaba en caché ~15 min y todo envío a esa persona fallaba. Ahora se vuelve a preguntar a los 5 s, y un mensaje de un dispositivo desconocido renueva la lista.
  • Envíos al mismo chat sin await (o con asyncio.gather, o por WebSocket) podían salir desordenados: ~30 de 300. Ahora salen en el orden en que se llamaron.
  • connect() justo después de disconnect() se quedaba desconectado.
  • Un mensaje que esperaba su reintento se olvidaba al reiniciar: no llegaba ni messageLost ni messageRecovered, y stats().lost se quedaba corto. Ahora la espera se guarda en el store (awaiting-retry).
  • Python: si salías de events() a la mitad de un lote, el resto del lote se perdía.
  • Las reacciones a tus estados llegan como <status type="reaction"> y no se confirmaban: WhatsApp cortaba la conexión 50 minutos después y la volvía a mandar en cada reconexión, para siempre. Lo encontró la prueba larga con un número real (17 reconexiones forzadas en 19 horas) una vez que el motivo de la desconexión empezó a traer el nodo completo.
  • Dos hilos podían guardar la misma sesión Signal en orden invertido y dejar un ratchet viejo en el store. La ventana era de nanosegundos y nunca se vio, pero ahora cada sesión se guarda antes de soltar su lock.
  • Node: un listener que tiraba excepción cortaba los eventos, y una promesa rechazada podía tumbar el proceso.
  • Python: una excepción en un handler paraba run().
